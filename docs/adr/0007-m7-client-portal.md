## D1 · 4 主栏 + 15 二级页：报告列表/总览合并进「报告」主栏

**背景**

现状 C 端是「双 Tab（首页 / 我的）+ 9 个天赋二级页」：`pages/index/index`、`pages/me/me`、`pages/talent/report/{list,overview,catalog,item}`、`pages/talent/interpretations/index`、`pages/talent/binding`、`pages/talent/plans/index`，另有账户流程页 6 个。PRD §5.2（L122–140）要求 4 主栏（首页 / 报告 / 培养方向 / 我的）+ 15 二级页，报告主栏直接是「对象条 + 页签 + 分册目录」，培养方向是「推荐 / 已选」两页签。UX 基线 U1 已把这个差距列为 M7 第一风险。

矛盾点：任务口径要求覆盖「报告列表 / 总览 / 目录 / 条目」四层，但 BR-02（L98）规定一人一份报告，PRD §7.3 的报告页没有独立列表层。若机械保留四层，会出现「一个对象的报告列表只有一张卡」的空转页面，与原型 2026-11-14 明确「首页去掉 XX 的基因报告卡」「报告页直接列六册」的收敛方向相反。

**选项**

1. **严格按 PRD：4 主栏 + 15 二级页；报告列表/总览合并进报告主栏，分册页=目录、要素解读=条目；注销收进「我的」弹层，不占二级页。**
2. 保留旧四层：报告列表 → 总览 → 目录 → 条目，二级页变 16–17 个，与 PRD 4+15 不一致。
3. 只做 4 主栏 + 页签内嵌所有内容，不做分册/要素二级页（SPA 式单页），返回栈与深链退化。
4. 沿用旧双 Tab，仅给首页加「报告/方向」入口，最小改动。

**结论**

选 1。理由：

- PRD §5.2 与 §7.3 是验收口径；BR-02 一人一份决定了「列表」没有存在价值。把「报告列表/总览/目录/条目」映射为「报告主栏（总览 + 六册列表）/ 分册页（目录 + 要素行）/ 要素解读（条目）」既覆盖四层信息，又不制造空转页面。
- 15 个二级页按原型四栏口径固定为：登录、账号停用、切换对象、分册页、要素解读、培育建议（独立页）、建议书、方向详情、选择方向、编辑资料、孩子管理、孩子信息、用户协议、隐私政策、关于。报告主栏内的页签与弹层（档位、确认框）不计数；注销是「我的」内的二次确认动作，不占页面。
- 选项 2 的列表层在真实数据下永远只有 0/1 行，且与「发布即冻结、一人一份」的模型冲突；每次多一层导航只增加点击成本。
- 选项 3 把分册/要素塞进单页会让长报告（6 册 × 多章）变成巨型滚动页，且无法深链到分册/要素、无法做分册 PDF 底部操作，违反 PRD §7.4 的页面形态。
- 选项 4 直接违反 PRD §5.2/§12 的 4 栏要求，且保留旧页面会继续依赖旧 bindings/旧报告字段（M6 已删除），技术上不可行。

**后果**

- 路由固定为 19 条（4 主栏 + 15 二级页），`pages.json` 不注册原生 tabBar；新增/删除页面需新 ADR 并同步验收计数。
- 旧天赋四页收敛为三页：`list`+`overview` → 报告主栏，`catalog` → 分册页，`item` → 要素解读；`interpretations` 并入要素解读；`TALENT_REPORT` 旧列表/总览不再存在。
- 深链与返回栈按 spec §2.3：Tab 根页是独立栈底，二级页入栈返回；冷启动深链栈深=1 时返回回主栏。
- 若客户后续坚持「报告列表/总览」独立页面，需新增页面并突破 4+15 计数，必须新 ADR + 更新 PRD 验收。

## D2 · 旧双 Tab / 旧页面迁移：保留路径的保留、天赋页整体替换，不做旧路由别名

**背景**

M2 重建了 bindings 契约（`items/currentId/...`，旧页读 `items[].customer.*` 已不兼容）；M3 重建了报告归属（`subjectType/subjectId`，旧页按 `customerId` 读取）；M6 §7.2/§7.3 删除旧 `binding.get.ts`、`bindings/[customerId].put.ts`、`plans.get.ts`、`plan-selections.*` 与旧页 `talent/binding.vue`、`plans/index.vue`，并要求 M7 覆盖报告页/分册/要素解读/切换对象后 M6 才能关闭「旧入口 0」验收。CLIENT-PORTAL 当前描述的是旧双 Tab 与旧报告四页，文档与实现都停在 M6 前。

**选项**

1. **路径保留 + 内容重写**：认证/资料/协议/隐私/关于/注销继续用原路径（`pages/auth/login`、`pages/profile/edit`、`pages/agreement/index`、`pages/privacy/index`、`pages/about/about`、`pages/account/delete`）；天赋页整体替换为 4 栏新路由；旧天赋页删除；不保留旧路由别名。
2. 全量重命名（连认证页也换新路径），一次性统一目录结构，但需要改 OAuth 回调/文档/测试。
3. 保留旧路由空壳页 + `redirectTo` 到新路由，兼容潜在深链。
4. 保留旧页并只加 4 栏入口，新旧并存。

**结论**

选 1。理由：

- 认证/资料/协议/隐私/关于是 Foundation 中性能力，路径稳定、与天赋业务无关；保留路径可减少 H5 深链、微信 OAuth 回调、文档与 e2e 的改动面。
- 天赋页必须整体替换：旧页依赖旧 bindings/旧报告字段，M6 删除旧接口后旧页本身就是坏的；保留只会让错误的读取口径残留。
- 不选 3：空壳别名页会增加页面数（突破 4+15），并让旧代码/旧字段继续留在构建产物中；C 端尚未对外发布，没有存量深链需要兼容。上线后如确需改路由，再新 ADR 加空壳页。
- 不选 4：新旧并存意味着两套数据契约、两套对象切换、两套报告页同时维护，是 M7 返工与串号的最大来源。

**后果**

- 删除清单：`pages/index/index.vue`、`pages/me/me.vue`、`pages/talent/**`（含 `components/TalentChildSwitcher.vue`）、`pages/account/delete.vue`（注销改弹层）、`store/talent.ts`、`utils/talent-presentation.ts`；`api/talent-types.ts` 重写。
- 保留并重写：`pages/auth/login`、`pages/profile/edit`、`pages/agreement/index`、`pages/privacy/index`、`pages/about/about`；`modules/foundation-portal` 的认证/主题/Tabbar/守卫/文档基础能力保留并扩展。
- 报告入口统一到报告主栏；旧报告 PDF 直链字段（`pdfUrl`）不再被 C 端读取，PDF 走新代理（D7）。
- M6 验收：M7 合并后方可关闭 C 端「旧入口 0」；M7 未合并前 M6 按书面豁免放行并记录风险。

## D3 · Wot UI 优先：能用 `wd-*` 就不用原生，原生只留微信开放能力

**背景**

UX 基线（2026-11-16）显示现状 Wot 基础良好：`@wot-ui/ui@2.2.0`、`wd-*` 128 处、原生表单/按钮 0 处、`--foundation-*` 499 处、组件内硬编码颜色 0 处、Emoji 图标 0 处。缺的不是「组件没用 Wot」，而是 4 栏/15 页重建、390/340 视觉基线、微信真机安全区、状态完整性（U1–U7）。同时 `wot lint` 有 12 条已知 warning（子组件未被 CLI 收录、2 条图标按钮已有 `aria-label`）。

**选项**

1. **Wot 最高优先 + 明文例外清单**：按钮/输入/选择器/单元格/弹层/页签/反馈/图标一律 `wd-*`；只有微信开放能力（`getPhoneNumber`、`chooseAvatar`、`input type="nickname"`、`open-type="share"`）与 `uni.downloadFile/openDocument` 用原生；原生控件统一重置样式；lint 例外清单化。
2. 允许页面自由选择原生控件，只要视觉接近。
3. 全部自绘组件，摆脱组件库版本差异。
4. 混合：核心控件用 Wot，业务卡片全部自绘（现状已接近）。

**结论**

选 1。理由：

- AGENTS.md 与 CONVENTIONS.md 已把「Wot 优先」定为硬规则；组件库统一了尺寸（48px 按钮）、深色映射、表单校验、弹层与无障碍基础，重写成本远高于收益。
- 微信开放能力没有 Wot 封装，必须保留原生；但只有这 5 类，且必须重置默认样式（边框、圆角、背景、行高、tap highlight）。
- 选项 3 会让主题令牌、暗色、无障碍、表单校验全部自建，与「不新增重复组件样式」冲突，也超出 10–12 人天。
- 选项 2 会重演历史「原生标签堆砌」，且小程序与 H5 默认样式差异大，视觉验收不可控。
- lint 的 12 条是 CLI 收录问题与已带 `aria-label` 的图标按钮，不构成质量问题；用「已知例外 + 新增即阻塞」比全局关闭规则更可持续。

**后果**

- spec §12.1 的决策树与「页面 → 组件映射」是强制项；页面不得直接堆 `<button>/<input>/<select>`。
- 原生控件只允许出现在：手机号授权按钮、头像选择按钮、昵称输入、分享按钮（如启用）、PDF 下载/打开调用。
- `wot lint` 已知例外清单入验收证据；新增 warning 阻塞合并。
- 图标一律 `wd-icon` 或项目内联 SVG；禁止 Emoji 当 UI 图标。

## D4 · 主题只跟随后台站点：不提供用户侧外观开关

**背景**

C 端现有 `useSiteStore` 从 `GET /api/client/config/site` 读取唯一站点的 `primaryColor` / `themeMode`，派生 `--foundation-*` 并映射 `--wot-*`；B 端后台的亮暗是管理员本机偏好，不回写站点配置。AGENTS.md / CLIENT-PORTAL / CONVENTIONS §4 都明确 C 端「不提供用户侧外观设置」。

M7 重建时容易出现两类退化：一是为了「深色友好」在页面加本机主题开关；二是把 Wot 默认蓝白主题或硬编码品牌色带回来。PRD §11 要求「后台与 C 端同一数据源」，主题也属于这条一致性。

**选项**

1. **只读站点配置**：`themeMode ∈ light/dark/system`，颜色/字号/间距全部走令牌；无任何用户侧外观入口；不写回站点配置。
2. 提供本机亮暗开关，默认跟随站点。
3. 按系统深色自动切换，忽略站点 `themeMode`。
4. 允许页面级局部色（如报告封面渐变）脱离令牌。

**结论**

选 1。理由：

- 客户是单一品牌、单实例；外观属于运营口径，不应由家长各自设置，否则客服/截图/验收无法复现。
- 现有令牌体系已覆盖亮/暗、状态色、字号、间距、圆角；`themeMode=system` 已在 store 中实现，用户想要「跟随系统」由后台配置即可，不需要 C 端开关。
- 选项 2/3 会让「后台改色 → C 端不一致」，违反 PRD §11 一致性与 PRD 主题口径；选项 4 会让暗色对比度失控（UX 基线 U7 已提示视觉资产需统一）。
- 报告封面渐变（`--foundation-cover-grad`）等已有令牌属于既有设计资产，保留在令牌层，不在页面硬编码。

**后果**

- 页面/组件只允许 `var(--foundation-*)`、`var(--fs-*)`、`var(--sp-*)`、`var(--wot-*)`；`rg` 检查硬编码色值 0 命中（`store/site.ts` 与 `style/index.scss` 的令牌定义除外）。
- 不新增「外观设置」页/入口；不写 `site_config`；不新增本机主题 key。
- 后台改主色/亮暗后，C 端下一次启动或 10s 同步内生效；暗色截图纳入验收矩阵。
- 若未来客户要求「家长可切亮暗」，需新 ADR 并改 PRD 口径。

## D5 · 对象切换：本机视图偏好 + 服务端每次重新鉴权，越权 404

**背景**

旧实现把「当前报告对象」存在服务端绑定记录里（`talent_customer_bindings` / `isCurrent`），并在 GET bindings 里写库；M2 已改为 `talent_parents.userId` 唯一 + 显式 `claim`，明确「当前对象由 C 端请求参数携带，服务端不持久化」（ADR 0002-D3）。旧 C 端按 `customerId` 读报告，M6 删除这些路由，M3 报告改按 `subjectType/subjectId` 归属。

原型曾出现「给二宝选方向写进一宝报告」的串号 bug（README 2026-11-14 九十四轮），根因是「当前对象没有报告时回落到家长名下任意一份已发布报告」。M7 必须从契约层杜绝。

**选项**

1. **本机记忆 + 请求显式携带对象/报告标识 + 服务端重新鉴权**：本机按 `userId` 存 `{subjectType, subjectId}`；summary 支持 `?subjectId=`；报告/建议/方向用 `reportId` 定位；服务端只认登录态解析的 parent，越权/非法 404；不写 `isCurrent`、不建绑定表。
2. 服务端持久化 `isCurrent`（回到旧模型）。
3. 只用 URL 参数传递对象，不记忆（每次切页丢对象）。
4. 服务端返回一个「当前对象」签名字符串，C 端原样回传。

**结论**

选 1。理由：

- M2/M3/M4/M5 的守卫都要求「只按 `talent_parents.userId` 解析 parent，不接受前端传 `parentId`」；把当前对象放服务端会重新引入并发写与「谁是当前」的二义性，也会让 GET 产生副作用（M2 明确 GET 只读）。
- URL 参数 + 本机记忆的组合既支持深链/刷新，又不需要服务端状态；按 `userId` 隔离避免多账号串。
- 选项 2 与 ADR 0002-D3 直接冲突；选项 3 在 tab 切换/返回时丢对象，体验差；选项 4 是「服务端状态」的变体，仍需写入与失效管理，无收益。
- 防串号的关键不是「记住对象」，而是「每个数据请求都绑定 reportId/对象，并由服务端校验归属」；本机记忆只是 UI 偏好。

**后果**

- 本机 key：`foundation:talent:subject:<userId>`；退出/注销/切账号/对象失效时清除；失效自动回退本人并提示。
- summary 的非法/越权 `subjectId` → 404；报告/分册/建议/方向接口的 report 归属校验失败 → 404（不泄露存在性）。
- 本机缓存不含报告内容；不缓存跨会话 PII。
- 切换页只写本机 + `navigateBack`，来源页 `onShow` 重载；禁止「无当前对象报告时回落到任意报告」。
- 解绑/停用/撤回后下一次请求立即失效；服务端不缓存。

## D6 · 登录退化矩阵：小程序手机号为主、H5 账号密码、游客可浏览、停用进停用页

**背景**

现有 C 端登录：小程序手机号一键（`open-type="getPhoneNumber"`）+ H5 账号密码（`#ifdef H5`）+ 游客；微信登录接口存在但 UI 未主推。M2 claim 依赖 `users.phone` 的 HMAC 命中 `talent_parents.mobileHash`，因此「手机号授权」是家长档案自动认领的关键路径；没有手机号时只能进入「未关联档案」状态。

PRD §7.1 要求「品牌标识 + 产品名 + 一句话说明 + 协议勾选 + 微信一键登录」，未勾选不可登录，停用显示停用页；§12 还要求 0 控制台错误、H5/小程序双端。M7 需要明确失败/降级路径，避免「授权失败就白屏」或「无手机号就无法使用」。

**选项**

1. **分层退化**：小程序「手机号一键」为主 → 拒绝则「微信登录」兜底（无手机号，进未绑定/联系客服）→ 都失败给可读提示与重试；H5 只做账号密码（不接 OAuth），忘记密码联系后台；游客可浏览首页/我的，业务页引导登录；停用统一停用页；401 回登录并回跳；注销走二次确认。
2. 只保留微信手机号一键，拒绝授权即不可用。
3. 增加短信验证码/找回密码/自助注册，做成完整账户体系。
4. H5 也接微信 OAuth，统一微信登录。

**结论**

选 1。理由：

- 手机号是 claim 的唯一可靠输入；但拒绝授权不应导致完全不可用，微信登录能保证「先成为账户」，再由客服/后台补齐手机号并认领。
- H5 接 OAuth 需要 AppSecret、回调域名、子路径同步，属于账户域扩展，不在 10–12 人天与本次报价范围；账号密码已能满足 H5 演示与内部使用。
- 选项 2 与微信授权可被拒绝的现实冲突，会把「拒绝一次」变成永久不可用；选项 3 引入短信服务商、验证码风控、密码找回，是新项目范围；选项 4 与「H5 仅账号密码」的现状和最小闭环冲突。
- 停用/过期/注销必须有明确落点，否则会出现「白屏 + 无限重试」或「token 失效仍显示已登录」。

**后果**

- 小程序登录页只出现微信授权入口（手机号为主、微信兜底），H5 只出现账号密码表单，编译期隔离，互不进入对方产物。
- 协议勾选是登录前置；未勾选按钮 disabled，不发请求；协议/隐私页可返回保持勾选。
- 停用页不可进入主栏；401 清会话 + 回跳（`redirect` 白名单校验，防开放重定向）。
- 注销无独立页面，二次确认 + 勾选确认；成功后清全部本地状态。
- 未绑定家长：自动 claim 一次 + 手动「重新匹配」；不提供邀请码/会员编号手动绑定（不在范围）。
- 手机号在 C 端是否可编辑仍未决（spec §18 U1），默认只读。

## D7 · PDF：M7 只做权限代理与下载交互，渲染/水印/时效归 M8

**背景**

PRD §7.4 要求分册页底部「下载本册 PDF」（仅开放册）；§10.4 要求「不暴露对象存储直链，走服务端签名/代理，带时效与水印」；§13.1 明确「PDF 渲染、水印、时效地址、下载留痕与权限代理」是原型未实现、正式版必须补齐的能力。M3 §8.4 与 ADR 0003 已冻结边界：M3 不生成/上传/删除 PDF，旧 `pdfUrl` 字段保留在旧行、新行不写；M8 负责按快照渲染、存储/下载代理、时效与水印。

现状 C 端仍有旧 `/api/client/talent/reports/:id/pdf` 路由读旧 `pdfUrl`，M6 删除旧报告路由后该能力不可用；M7 必须给新的代理契约，否则分册下载入口会指向死链。

**选项**

1. **M7 落代理路由 + 门禁 + 下载/打开交互；M8 提供真实文件/渲染与时效水印**：M8 前代理返回 `404 PDF_NOT_READY` 与可读文案，按钮置灰或点击提示；不伪造、不复用旧 `pdfUrl`。
2. M7 直接用旧 `pdfUrl`/旧代理，等 M8 再换。
3. M7 自己实现 PDF 渲染/水印/存储（提前做 M8）。
4. M7 不做下载入口，等 M8 一起上。

**结论**

选 1。理由：

- 报价/开发计划把 PDF 渲染归 M8；M7 提前做会与 M8 的模板/水印/存储方案冲突，且 10–12 人天不含渲染引擎与文件服务。
- 选项 2 会让新报告（M3 新行不写 `pdfUrl`）全部 404，并继续暴露旧直链语义；选项 3 越界且高成本；选项 4 让 PRD §7.4 的分册下载入口缺失，验收无法覆盖页面交互。
- 代理路由先落地可以把「归属 + 报告状态 + 开放册」三个门禁固定下来，M8 只需在 seam 内返回文件流；页面交互（小程序 `downloadFile`+`openDocument`、H5 新窗口）也可提前验收。

**后果**

- 新路由：`GET /api/client/talent/reports/:id/volumes/:volumeId/pdf`；门禁与报告/分册接口一致；未就绪 `404 PDF_NOT_READY`（文案「本册 PDF 暂不可下载」）；`cache-control: private, no-store`；不返回直链。
- 与 PRD §9 L575 的 `/reports/:id/download`（整份下载）存在偏差：PRD §7.4 明确「下载本册 PDF（仅开放册）」，故按分册路由；整份打包下载不在 M7 范围，M8 如需再加聚合路由。
- M7 验收中 PDF 项标记「未验证（依赖 M8）」或「部分通过（门禁/交互）」；不得伪造通过。
- M8 接入时保持不变式：页面只消费代理地址；水印/时效/下载留痕在服务端；日志不记 PII。
- 旧 `pdfUrl`/`pdfFileKey`/`pdfFileName` 与旧代理不再被 C 端使用。

## D8 · H5 / 微信小程序差异：编译期隔离平台能力，业务与文案共用

**背景**

同一套 uni-app 代码要出 H5 与微信小程序。差异集中在：登录方式（H5 账号密码 vs 小程序微信授权）、请求地址（H5 代理/同源 vs 小程序合法域名 + `envVersion` 三套地址）、PDF 打开（新窗口 vs `downloadFile+openDocument`）、头像（系统选择器 vs `chooseAvatar`）、键盘/安全区/胶囊、分享、DOM 可用性、包体限制。现有 `http.ts` 已做 `#ifdef` 分支与小程序地址校验；`manifest.config.ts` 配 `VITE_WX_APPID`。

风险是平台分支写进业务逻辑，导致两端行为漂移，或小程序误用 `window/document` 在真机白屏。

**选项**

1. **平台分支只包 API 调用**：业务逻辑、文案、状态映射、主题共用；`#ifdef H5` / `#ifdef MP-WEIXIN` 只包登录入口、地址解析、下载/打开、头像、键盘/胶囊适配；小程序禁用 DOM；包体控制。
2. 两套页面代码（H5 一套、小程序一套），最大化平台适配。
3. 只做小程序，H5 作为降级预览不保证。
4. 用运行时 `uni.getSystemInfoSync().platform` 分支，不做编译期隔离。

**结论**

选 1。理由：

- 报价与 PRD §11 要求 C 端同时支持「微信小程序 + H5」；两套代码会让 19 页 × 2 份维护，远超 10–12 人天，且状态/文案必然漂移。
- 编译期隔离能保证「H5 产物不含微信授权按钮、小程序产物不含账号密码表单」，也避免运行时分支把两端差异扩散到业务层。
- 选项 2/3 违反交付范围；选项 4 会把两端差异带进运行时，且无法 tree-shake 平台专属代码（包体、合规都受影响）。

**后果**

- 目录内平台分支只出现在 `http/api-url`、登录面板、头像上传、PDF 打开、键盘/胶囊适配等少数文件；业务组件不出现 `#ifdef`。
- 小程序不使用 `window`/`document`/`localStorage` DOM API，统一 `uni.*`；H5 提供 `:focus-visible`。
- 请求地址：H5 走 `VITE_SERVER_BASEURL`/`VITE_APP_PROXY_*`；小程序按 `envVersion` 选 `VITE_SERVER_BASEURL__WEIXIN_{DEVELOP,TRIAL,RELEASE}`，生产必须 HTTPS 且加入合法域名。
- 包体：不把 PDF 解析器、图表库、大图打进主包；新增页面不引入大依赖。
- 验收：两端各自 build + `client:check:wxss` + 真机（iOS/Android 微信）+ H5 390/340；平台差异清单进 acceptance 证据。
