## D1 · 验收唯一事实源：PRD §12 + 模块 acceptance + M9 矩阵三层，M9 必须重新取证

**背景**

M1–M8 各有 `acceptance.md`，成熟度差异很大：M1 已验收但仍有 2 条未验证（依赖 M3）、M2 为「有条件通过」（页面运行态 U1 未复跑）、M3 实现完成待验收、M4 纯函数完成且 M4-B 进行中、M5-A/B 完成且 M5-C 进行中、M6/M7/M8 尚未实现。PRD §12 是客户验收总表；`docs/QUALITY.md` 是工程门禁；`docs/STATUS.md` 是现状快照。三处都可能被引用为「是否可发布」，但没有任何一处单独覆盖「FR/AC/BR + 模块 AC + E2E + 性能 + 安全 + 发布」的全集。

矛盾点：如果 M9 直接汇总各模块自报的「通过」，会把模块内部口径（如 M2 的 U1 页面运行态未复跑）带进发布结论；如果 M9 另起一套需求，又会与 PRD 漂移。M9 需要的是「事实源分层 + 重新取证规则」，而不是第三套需求。

**选项**

1. **三层事实源**：PRD §12（需求）→ 模块 acceptance（模块证据）→ M9 矩阵（发布事实源）。M9 按矩阵逐条重新取证，模块结论只作现状参考；模块 AC 全部纳入 M9 汇总。
2. 直接把各模块 acceptance 的通过率加权汇总为发布结论。
3. 以 PRD §12 为唯一表，模块 acceptance 失效。
4. 新建一份独立「客户验收清单」，与 PRD/模块脱钩。

**结论**

选 1。理由：

- PRD 是商务与客户的唯一需求源，不能被实现口径覆盖；模块 acceptance 提供「实现到证据」的细节，是 M9 的执行底座，但其状态会随实现漂移，不能直接当发布结论。
- M9 矩阵把 FR/AC/BR/模块 AC 合并到同一张可判定表，并强制每行给「实现落点 + 测试/证据 + 状态」，才能回答「发布还差什么」。
- 选项 2 会把「有条件通过」「未验证」洗成通过，风险最高；选项 3 丢掉模块级证据链；选项 4 制造第二套口径，验收会必吵架。
- M9 的产出还包括 E2E、性能、安全、发布门禁，这些不属于任何单个模块，必须有独立的发布事实源。

**后果**

- M9 矩阵（spec §3）中所有条目初始 `未验证`；只有拿到命令/步骤 + 退出码 + 关键输出才可改状态。
- 模块 acceptance 链接保留，M9 抽查其关键证据；抽查失败按模块回退，不修改模块文档冒充。
- `docs/STATUS.md` 在 M9 出口更新门禁结果，但不复制会漂移的大表；以 M9 acceptance 为准。
- 客户签字页以 M9 acceptance 的通过率与差异清单为附件。

## D2 · E2E 两层重写：01–05 冒烟 + 06–10 验收，隔离实例、可重复两次

**背景**

现有 `scripts/e2e/01–05` 面向 2026-09 旧口径：01 覆盖分类/要素/内容库/内部模板/旧会员；02 覆盖绑定/阶梯/内容库/报告类型/匹配预览/旧报告发布/机构与授权/同步配置/机构端数据范围；03 覆盖旧 webhook 与旧 CSV 导入；04 覆盖旧 C 端四层报告页与培养计划；05 覆盖 16 个旧后台页与「客户管理员看不到系统管理」。M1–M5 已建立新域，M6 将删除旧集合/旧页面/旧 API，M7 重建 C 端，M8 替换外部接入。旧套件继续存在会同时产生「必红」与「假绿」：必红是因为旧入口被隐藏/删除；假绿是因为断言打旧 API，新域未被覆盖。

同时，旧套件有结构性卫生问题：02 用固定机构编号且不清理，连续跑第二次必失败；01–03 在共享演示库上写数据；报告不可删除（TAL-08），02 会把报告转「已撤回」并留在 03 的 webhook 报告；远端跑完必须带库重部署。M9 不能继承这些问题。

**选项**

1. **两层套件**：01–05 冒烟（快、稳、每次可跑），06–10 领域验收（慢、逐 AC、发布门禁）；隔离实例 + 随机后缀 + 跑前备份/跑后恢复；扩展 `lib.mjs`/`run-all.mjs` 支持分组、超时、证据 JSON。
2. 只重写 01–05 覆盖全部新域，不新增 06–10。
3. 保留旧套件，新增 06–10，旧套件标记 skip。
4. 引入外部测试平台（Cypress/自建）重搭。

**结论**

选 1。理由：

- 冒烟/验收分层是质量门禁的常识：日常改动需要 5–8 分钟可跑的 01–05；发布门禁需要逐 AC 的 06–10，两者对数据准备、运行时长、失败容忍不同，不能混成一套。
- 06–10 按域切分（会员/报告/建议/方向/C 端与权限回归）与 M2–M7 的 AC 一一对应，失败能直接定位模块与 AC。
- 隔离实例 + 快照恢复是「报告不可删除」约束下唯一能保证复跑一致的做法；固定编号/不清理的老问题必须从设计上消除，而不是靠「跑前重置」提醒。
- 选项 2 会让一次失败重跑成本过高、冒烟不再快；选项 3 的 skip 等于长期不跑，且旧套件会持续腐烂；选项 4 超出单实例交付范围，且 Playwright 已在仓库、能覆盖 H5/后台。
- 小程序原生端仍需开发者工具与真机（M7 G7），E2E 只覆盖 H5；这是明确边界，不假装覆盖。

**后果**

- M9-B 落地 `01-foundation-rules-crud`、`02-rules-actions`、`03-ingest-sync`、`04-client-main`、`05-admin-ui-permission`、`06-member-domain`、`07-report-domain`、`08-advice-domain`、`09-direction-domain`、`10-client-permission-regression`；`run-all` 增加 `--group smoke|acceptance|all`、单套件超时、`summary.json`。
- 验收套件只允许隔离实例；`E2E_TARGET=remote` 仅 staging 且 `E2E_ALLOW_WRITE=1`；生产域名硬拒绝；远端跑完用备份恢复，不再依赖 `--with-db --force-db-replace`。
- 每个套件必须连续两次全绿；缺 Playwright/服务/种子时 fail-fast，不得 skip 冒充通过。
- 旧套件的「机构/培养计划/内容库/同步配置」断言全部改为「0 命中/404」，不保留「应存在」断言。

## D3 · 性能门槛固定且可复现：1000 会员 / 500 报告 ≤2s，C 端 1.5s，PDF/同步分级

**背景**

PRD §11 要求「后台列表首屏 ≤2s（1000 条内）；C 端报告页首屏 ≤1.5s；分册要素按需加载」，但没有定义数据规模、测量方法、失败判据；M3 acceptance 的 V7 把「快照 JSON 体积/1000 条列表性能」留给 M9；现有 STATUS 只有规模数字，没有性能基线。没有固定数据集与方法，性能结论不可复现，也无法判断回归。

**选项**

1. **固定门槛 + 固定数据集 + 中位数/p95**：1000 会员/500 报告/500 建议；列表首屏 ≤2s、C 端 1.5s、PDF 冷 10s/热 2s、同步 100 人 2min/500 人 10min；本地隔离环境、预热 3 次、10 样本。
2. 只做「不卡」的人工体感检查，不设硬门槛。
3. 用开发库现有小数据（8 会员/7 报告）测首屏。
4. 上生产后再看监控，不设发布前性能门禁。

**结论**

选 1。理由：

- PRD 已给硬指标，M9 只需把「规模 + 方法 + 判据」补全；中位数 + p95 能同时反映常态与抖动，避免单次偶然。
- 固定数据集（1000/500）是复现的前提；选项 3 的小数据测不出分页、快照 JSON、索引缺失的问题，是最常见的「假通过」。
- PDF 与同步没有 PRD 数字，但属于主链且成本高，必须有独立门槛；冷/热分离避免缓存掩盖真实渲染成本。
- 选项 2/4 把风险推到生产，违反「发布前门禁」；生产监控保留，但不能替代发布前测量。
- 性能门槛只在发布门禁执行，不要求每次提交都跑全量，避免拖慢日常开发。

**后果**

- M9-C 提供 fixture 生成与测量脚本（隔离库专用），输出 `P-01..P-10` 证据；数据集、分页参数、筛选条件、机型/版本必须写进证据。
- 超门槛阻断发布；退化 >20% 即使未超门槛也要记录并评估。
- 单页网络请求 ≤5、接口调用 ≤3，作为 N+1 的硬判据；逐行请求直接失败。
- 不达标时优先查索引/两段查询/快照体积/序列化，不允许通过缩小分页、删数据、关鉴权达标。

## D4 · 安全门禁五类：越权矩阵、脱敏与日志、文件/PDF、密钥 P0、依赖审计

**背景**

PRD §10 要求：家长只能访问本人与已绑定子女；敏感字段默认脱敏、全号需独立授权并写日志；关键动作审计；PDF 不暴露直链；接口按角色鉴权。M2 已落三件套加密与 bindings，M3/M5 有 C 端守卫，M7/M8 定义 PDF 代理与存储。但安全结论分散在各模块，没有一张跨角色/跨对象的越权矩阵，也没有「日志无明文」「存储直链」「依赖漏洞」的统一门禁。另有已知 P0：`.env`/`.deploy.env` 被 Git 跟踪，含 OSS AK/SK、服务器口令与超管密码（STATUS §7），用户已明确暂缓修复。

矛盾点：P0 密钥是发布阻断项，但用户要求暂缓；如果 M9 把它写成「已处理」或直接忽略，都会失真。必须把它登记为「未修复、阻塞生产、不阻塞开发」，并明确解除条件与责任人。

**选项**

1. **五类门禁 + P0 如实登记**：越权矩阵（匿名/四角色/C 端跨对象/停用/解绑）、脱敏/全号/日志扫描、文件与 PDF 门禁、密钥 P0（生产硬门禁、开发豁免）、依赖审计；P0 不修复但每份发布证据都显示状态。
2. 只做功能测试，安全交给代码 review。
3. 一次性修复 P0 密钥（改写 Git 历史 + 轮换）后再做 M9。
4. 把 P0 记成「已知风险」但不进门禁。

**结论**

选 1。理由：

- 安全必须有可判定的矩阵与扫描证据，代码 review 不能替代「越权返回码、响应无明文、日志无 PII、直链不可读」的实测。
- P0 密钥的处置权在用户/lead，M9 无权也不应擅自轮换或改写历史；但发布门禁必须让它可见，否则等于用文档掩盖风险。
- 选项 2 会漏掉 C 端跨对象/撤回/未开放册等高风险分支；选项 3 超出 M9 范围且可能破坏协作中的仓库；选项 4 会让 G9 形同虚设。
- 「不阻塞开发」是用户明确口径：本地/隔离实例继续用现有 `.env`，但不得对外演示生产；生产发布前必须完成轮换与旧值失效验证。

**后果**

- spec §6 固定越权矩阵与期望码（401/403/404/409/410）；403 只用于「有身份无权限」，越权对象统一 404。
- 日志/响应/导出/证据包全部扫描手机号与身份证格式；允许白名单虚构示例号，但不得出现真实 PII。
- 文件门禁覆盖 PB `uploads` 与 OSS 双存储：私有、加密、代理、ticket 120s、水印、留痕、撤回即时失效。
- 密钥 P0 在 acceptance 中固定为 `未验证（P0 未修复）`；G9 只阻塞生产；解除需 `git rm --cached`、轮换全部密钥、旧值失效、`git ls-files` 无 `.env*`、历史处置决定。
- 依赖审计：`pnpm install --frozen-lockfile`、`pnpm audit --prod --audit-level high`；无法修复的漏洞需书面豁免（影响/缓解/到期日），由 lead 批准。

## D5 · 发布/回滚：G1–G10，备份与恢复演练硬门槛，代码与数据回滚分离

**背景**

`docs/QUALITY.md` 已有发布验收清单，`docs/OPERATIONS.md` 有部署/回滚/备份章节，但两者是分散的检查项，没有「门禁 ID + 判据 + 证据 + 责任 + 失败处置」的发布合同；M6 的破坏性清理需要整库恢复，M8 有多个功能开关与回滚顺序，单实例又不能做真正的灰度（PM2 cluster 被禁止）。现状容易在发布日临时判断，且「构建通过」常被误当「可发布」。

**选项**

1. **G1–G10 门禁 + 分阶段发布/观察 + 回滚矩阵**：代码/数据分离回滚；M6 只允许整库恢复；M8 按开关顺序回滚；发布前备份与恢复演练为硬门槛；单实例用「预发验证 + 低峰发布 + 开关 + 快速回滚」替代灰度。
2. 沿用 QUALITY 清单，不新增门禁编号。
3. 引入蓝绿/金丝雀部署（需要多实例/多 PB）。
4. 发布后出问题再回滚，不做发布前演练。

**结论**

选 1。理由：

- 门禁编号让「发布是否就绪」可被审计与引用；每道门禁有独立判据，避免「G3 过了就代表能发」的误解。
- 单实例是硬边界，蓝绿/金丝雀会破坏定时任务、进程内锁与本地文件的假设；用预发 + 低峰 + 开关 + 回滚是边界内可行方案。
- M6 删除集合后无法局部恢复，必须整库恢复；代码与数据回滚分离能避免「先启旧代码访问新 schema」的二次事故。
- 备份不演练等于没有备份；发布前恢复演练是 M6 的硬门槛，也应成为所有高风险发布的门槛。
- 选项 4 会把风险留给用户与线上数据，不符合「先保留证据再修复」的运维原则。

**后果**

- G1 代码/类型、G2 数据/schema、G3 矩阵、G4 E2E、G5 性能、G6 安全、G7 可观测、G8 备份回滚、G9 生产配置与密钥、G10 客户签字；G9 仅阻塞生产。
- 发布流程：T-3 门禁与备份 → T0 低峰 `deploy:remote -- --no-db` → T+0 探活/冒烟 → T+2h 观察 → T+1 记录与 STATUS 更新；触发阈值即回滚。
- 回滚矩阵：纯前端/新增字段/M6/M8/数据损坏分别定义；禁止 `git reset --hard`、删除 `pb_data/`、局部补集合、用 `env:setup` 覆盖存量库。
- M8 回滚顺序固定：关 PDF → 关调度 → 切源/关入站 → 代码回滚；回滚后验证 health/deep、C 端 PDF/同步日志、旧路由未受影响。

## D6 · PRD 差异签字：集中登记、默认口径先执行、未签字不算验收完成

**背景**

PRD §13 已列部分差异与待定项（补发后建议、报告撤回建议状态、复测、第四卡、归并入口、上限可配置、历史导出）。此外还有实现/规格层已定但 PRD 未写的差异：菜单扁平化（工作台/会员管理一级、培养方向并入天赋规则、系统管理/运行监控仅 superAdmin）、系统管理 10 页、C 端 4+15、手机号只读、PDF 按册、报告审核员保留发布权限、A–F↔V1–V6 映射、0 命中回退截断 5、别名不参与命中、水印手机尾号等。这些差异若只在各模块 spec 里，客户验收会时会被当成「漏做」或「擅自改需求」。

**选项**

1. **集中差异清单 + 客户签字**：M9 §9 汇总全部差异与待确认项，每项给 PRD 位置、当前口径、影响、状态/裁决人；已定项需客户签字，待裁决项默认口径先执行；签字是 G10。
2. 差异留在各模块 spec，验收会逐条解释。
3. 全部按 PRD 字面改实现（会恢复独立培养方向分组、平台运营系统管理、整份 PDF、手机号可编辑等）。
4. 只登记待定项，已定差异不告知客户。

**结论**

选 1。理由：

- 差异集中才能被客户一次性确认；分散在各 spec 等于没有验收口径。
- 「已定」不等于「客户已知」：菜单结构、系统管理权限、C 端页数、PDF 粒度都是客户可感知的行为，必须签字。
- 选项 3 会与 2026-11-16 用户口径、M6 清理、单实例安全边界冲突，属于倒退；选项 4 把风险留到验收会，必然返工。
- 默认口径先执行可以避免「等客户回复再开发」的停滞；裁决后只改读取层/配置/菜单授权，尽量不动数据模型。

**后果**

- spec §9 的 D-01..D-22 是唯一差异清单；新增差异必须补行并标裁决人，不得在模块 spec 私了。
- 「系统管理 > 机构管理」不是差异接受项：M6 必删，M9 断言 0；任何恢复机构域的改动直接违反红线。
- G10 签字页必须附差异清单与待裁决项；未签字只能写「技术验收通过、客户验收待定」，不得写「验收完成」。
- 客户裁决后：截止时间、默认口径、变更影响回写 spec 与 acceptance，并重跑受影响 AC。
