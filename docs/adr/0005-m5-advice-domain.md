## 背景

PRD 把培育建议定义为一个**外部系统推送、平台只同步与展示**的域：外部系统按基因报告、以「姓名 + 具体年龄（周岁）」匹配《天赋培育开发建议文库》，输出一册一份的建议书；平台每 4 个月接收一版，后台保留全部历史版本，家长端只读当前生效版本（PRD §6.7、§7.6、§8.2、§8.3、BR-06、BR-07）。它的关键约束与 M3 报告域、M2 会员域、M1 规则域都不同：

- 建议内容**不是平台生产的**，不能编辑、不能由 M1 要素/注解推导、不能由 M4 方向命中生成；
- 建议有**版本维度**，版本切换会让 C 端内容整体换一版，旧版必须只读留档；
- 建议与报告必须「同发」（BR-06），但 M3 已冻结「报告发布/撤回不改建议集合」，PRD §13.2-2 也明确当前只是「C 端不可见、后台仍已发布」；
- 建议按「精确周岁」匹配（不是区间），年龄会随版本重算；
- 仓库里已有旧 `talent_cultivation_contents`（要素 × 分级 × 年龄/性别的内容库）与旧建议相关代码，口径完全不同，不能沿用。

本 ADR 记录 M5 的 6 个关键决策与备选，给实现 agent 与后续 M6/M7/M8 一个稳定合同。

## D1 · 版本与生效版：版本行 + 建议行两层，`status="active"` 部分唯一索引保证单一生效版

**背景**

PRD §8.2 给出两张表：`advice_version`（id、name、status 当前生效/已归档、cycle、effective_at、next_update_at、synced_at、source、note、operator）与 `advice_doc`（按版本的建议书），§8.3 要求「已发布 ⇄ 已撤回；版本维度：当前生效 → 已归档」。需要定死：版本怎么存、当前版本怎么表达、历史版本怎么看、切换是否可回退。

**选项**

1. 只建一张建议表，`version` 作为字段；当前版本用「`syncedAt` 最大」推断。
2. 建版本表 + 建议表；当前版本用**配置项/指针字段**（如 `configs` 或一张单行表）指向。
3. 建版本表 + 建议表；当前版本用 `status="active"` 表达，配 **部分唯一索引** `UNIQUE(status) WHERE status="active"` 保证单一生效。
4. 建版本表 + 建议表；建 `isCurrent` 布尔，靠服务层维护唯一。

**结论**

选 3。理由：选项 1 无法表达「归档版本仍可回溯」「同一版本多份建议」且推断当前版在并发下不可靠；选项 2 与硬约束冲突（业务字段不得回填 `configs`），且新增一处「指针与版本行状态可能不一致」的双真源；选项 4 仍把唯一性交给应用层，PB 层面没有约束，并发接收新版可能产生两条 current。选 3 让数据库自己保证「最多一版生效」，服务层只需按固定顺序翻转（旧 active → archived、新 → active），读取端永远 `getFirstListItem('status="active"')`，无指针可漂移。同时**不提供**手动归档、删除版本、编辑版本、把历史版本切回生效的接口——PRD 只有「回到当前生效版」的**查看**行为，不是数据操作。

**后果**

- 表结构按 spec §3.1；索引 `idx_talent_advice_versions_active` UNIQUE(`status`) WHERE `status = "active"` 必须在新库断言存在（`sync-talent.mjs` 只加不删）。
- 版本接收写入顺序固定：先建 `archived` 占位版本 → 建建议行 → 旧 active 归档 → 新行激活；失败补偿删除占位与建议行、恢复旧 active（spec §4.3）。
- 归档版本永久保留、只读；列表/详情/导出可带 `versionId` 查看历史，但写动作对历史版本一律 409 `ADVICE_VERSION_READONLY`。
- 版本份数与发布统计**不落字段**，读取时聚合 `talent_advice_docs`，避免每次发布/撤回回写版本行造成计数漂移。
- 周期用常量 `TALENT_ADVICE_CYCLE_MONTHS = 4`（BR-07），版本行冻结 `cycle` 与 `nextUpdateAt`，不建配置表（PRD §13.3 未裁决可配置性）。

## D2 · 建议正文存 `sections` JSON（一份基因报告 × 一个版本一行），不建子表；列表用派生缓存字段

**背景**

PRD 原型与 §8.2 的 `advice_doc` 是「一份基因报告对应一份建议书」，`books` 记录覆盖分册（如 `ABCDEF`），`sections[]` 每条带 `book/book_name/chapter/factor/entropy/content/example/direction/suggestion/variant`。C 端要求「按分册展示、一册一份、各自编号」（PRD §7.6），后台建议书弹层也按分册分组（每册编号 = 建议编号 + 分册编码）。需要定死：建议书是一行一册，还是一行一报告？sections 是子表还是 JSON？

**选项**

1. 一行一册（每个基因报告 × 每个分册一行），`sections` 只存本册。
2. 一行一报告（每个基因报告 × 版本一行），`sections` 自带 `book` 字段，跨册混存。
3. 建 `talent_advice_docs` + `talent_advice_sections` 子表（一条 section 一行）。
4. 一行一报告 + `sections` 存外部原始 JSON 字符串，读时解析。

**结论**

选 2（+ 派生缓存字段）。理由：PRD §8.2 的 `advice_doc` 字段集是「报告级」（gene_report_id / report_no / name / id_no / match_key / books / sections[]），原型 `ADVICE_DOCS_RAW` 也是一报告一行、`books` 多册、`sections` 跨册；「一册一份、各自编号」是**展示与编号派生**（`{adviceNo}-{book}`），不是存储粒度。选项 1 会把 `name/id_no/books` 等报告级字段复制 N 份（6 册时冗余 6 倍），且版本历史/按人历史要按册聚合；选项 3 让「正文只同步不改写」的一句话变成多行一致性负担（部分写入即脏数据），且外部推送本身就是整份 JSON；选项 4 放弃 PB JSON 查询/展示能力，读时反复解析。

`variant` 保留：同一 `(book,chapter,factor,entropy)` 可能有多条话术变体（外部文库特性）；后台全部展示，C 端只返回 `variant` 最小的一条，避免同一个要素重复出现。

列表 15 列需要「覆盖要素 / 数据熵 / 建议书份数」，为不把整份 `sections` 读回列表，落 4 个**派生缓存字段**（`sectionCount` / `bookCount` / `entropyCounts` / `firstFactorName`），写入时由服务端计算，只读、无接口可单独修改，测试断言之可由 `sections` 重算。

**后果**

- 表结构按 spec §3.2；唯一键 `(versionId, geneReportId)`（同一版本一人一份建议书）+ `adviceNo` 全局唯一。
- `sections` 归一化/校验/排序在服务层完成（spec §3.3）：book ∈ books、entropy 白名单、四段 ≤2000 字、数组 ≤200、整份 ≤256KB、PII 正则拒绝；单条不合规 → 该对象 `failed`，不写半份。
- 列表/版本历史/导出**不返回 sections**；详情按份返回、按分册分组。
- 派生缓存字段不参与业务判断；发布/撤回不改（正文不可变）。
- 不存固定注解、不存要素编码：正文来自外部文库，不绑定 M1 `talent_factors` / `talent_factor_notes`（BR-12 编码不对家长展示）。

## D3 · 同步即发布：外部写入即 `published`；发布/撤回只改可见性；重复版本 409

**背景**

PRD §6.7 口径：「外部系统同步即默认已发布；后台逐份撤回后家长端立即不可见；正文只同步不改写」；§8.3 建议状态为「已发布 ⇄ 已撤回」。需要定死：同步来的建议初始状态、发布/撤回改什么、重复接收怎么处理、正文是否可被发布动作影响。

**选项**

1. 同步来先 `draft/待发布`，运营逐份确认后发布。
2. 同步来直接 `published`；后台只能撤回/重新发布；发布/撤回只改可见性。
3. 同步来 `published`，但发布动作会「重新写一遍正文/刷新时间」。
4. 同步来 `published`；重复接收同版本静默成功（幂等 200）。

**结论**

选 2。理由：PRD §6.7 与原型注释明确「同步即默认已发布」，选项 1 会让 4 个月一次的批量建议多一道人工发布，且与「家长端在报告发布后即可读建议」的验收（AC-ADM-07-3）冲突；选项 3 违反「正文只同步不改写」，也会让 `sections` 快照失去可复现性；选项 4 会让运营误以为「又同步了一次」，且无法暴露重复操作（M3 同样采用「重复动作 409，不静默成功」的处置）。

**后果**

- 新建建议行固定 `publishStatus="published"`、`publishedAt=syncedAt`、`withdrawnAt=""`（spec §4.2）。
- 发布：`withdrawn → published`，`publishedAt=now`、`withdrawnAt=""`；撤回：`published → withdrawn`，`withdrawnAt=now`、`publishedAt` 保留。两者都不改 `sections/books/age/matchKey`，都只允许当前生效版本，重复动作 409。
- 每次接收新版，新版内所有人重新从 `published` 开始（不继承上一版某人的撤回状态）。
- 重复接收（版本号 / 生效月份 / 生效日期任一已存在）→ 409 `ADVICE_VERSION_EXISTS` + `existingVersionId`，不写集合、不切版；并发由 `withTalentReportLock("advice:version")` 串行化。
- 写动作全部 `withOperLog`：标题「发布培育建议 / 撤回培育建议 / 接收培育建议新版本」，摘要含建议编号、版本号、姓名、份数，不含证件号。

## D4 · 撤回与 M3 联动：不双写状态，C 端可见性按「建议 ∧ 版本 ∧ 报告 ∧ 归属」派生

**背景**

BR-06 字面是「报告发布/恢复时，该对象当前周期的建议一并置为已发布；报告不可读时建议不可见」；但 M3 已冻结「M3 不写 `talent_advice_*`，报告发布/撤回/恢复不改建议集合」，PRD §13.2-2 也把「报告撤回时建议数据是否同步置已撤回」列为**待明确口径**，当前实现是「仅 C 端不可见，后台建议仍为已发布」。需要定死：可见性谁说了算、要不要双写、后台显示什么。

**选项**

1. 双写：M3 报告发布/撤回/恢复时，同步更新该对象建议行的 `publishStatus`。
2. 单向派生：报告只读影响建议可见性；建议行状态只由 M5 的发布/撤回改变；C 端可见 = 建议已发布 ∧ 当前生效版本 ∧ 报告已发布 ∧ 归属正常。
3. C 端各自读两表在页面层拼装：报告页判报告、建议接口判建议，两边不约定统一规则。
4. 给建议加一个 `effectiveVisible` 落库字段，由定时任务/触发器维护。

**结论**

选 2。理由：选项 1 是典型的双写漂移源——M3 的发布/撤回/恢复/补发/重算五条路径都要记得写 M5，任一遗漏就会出现「报告已撤回、建议仍可读」的安全缺口；而且「报告恢复」该把建议恢复成什么状态（原来被后台撤回的那份要不要也恢复？）没有口径。选项 3 把一致性交给页面，C 端两个接口不同步时会互相打脸。选项 4 引入后台任务与缓存过期窗口，违反「读时以 DB 当前状态为准、立即失效」的验收要求。选 2 后 BR-06 的用户可观察结果完全满足：报告发布 → 建议自动可见；报告撤回 → 建议立即不可见；报告恢复 → 建议自动恢复；而 M3/M5 各写各的集合，无跨模块写依赖（与 M3 spec §8.2、ADR 0003-D8 完全一致）。

**后果**

- 派生公式落在 `isTalentAdviceClientVisible(doc, report, parent, child)`，读取时计算，不落字段（spec §4.5）。
- 报告撤回/恢复**不改**建议行 `publishStatus`；后台 15 列「发布状态」只显示建议自身状态，详情信息条另给派生提示「家长端可见性：可见 / 不可见（报告未发布）/ 不可见（报告已撤回）/ 不可见（建议已撤回）」。
- C 端接口先按 M3 契约拒绝不可读报告（409 `report_pending` / `report_retracted`，与 M3 §7.1 同码同文案）；报告可读但没有已发布建议时返回 200 `{ available:false, emptyText:"暂未收到培育建议" }`。
- 家长停用 / 子女解绑同样即时生效（M2 归属解析，不缓存）。
- 单测必须覆盖「报告三态 × 建议两态 × 归属状态」组合，防止未来有人加双写。
- 若客户最终要求「报告撤回时建议也置撤回」（PRD §13.2-2 反面），需同时改 M3/M5、删除派生分支并新增一致性校验——ADR 需要改版，不在 M5 预留。

## D5 · 年龄口径：按同步日算精确周岁并冻结；matchKey = 姓名｜N 岁；列表精确相等

**背景**

PRD §6.7：「年龄（精确周岁）」；AC-ADM-07-2：「年龄按精确周岁匹配（输 7 只命中 7 岁）」；原型注释：「按姓名 + 具体年龄（周岁）→ 对应培育建议；7 岁就是 7 岁册，不按区间合并」；外部建议文库本身按「性别 + 年龄」分册。同时 M1 旧 `talent_cultivation_contents` 用的是 `minAge/maxAge` 区间匹配，是非常容易被误用的旧口径。需要定死：年龄什么时候算、存什么、按什么筛、跨版本怎么变。

**选项**

1. 存生日，查询时实时算周岁。
2. 存「同步时精确周岁」并冻结；列表按冻结值精确相等筛选；匹配键同步冻结。
3. 存 `minAge/maxAge` 区间（沿用旧 `talent_cultivation_contents` 思路）。
4. 存年龄区间标签（如「7–8 岁」）。

**结论**

选 2。理由：选项 1 会让「同一份建议书在不同日期查询得到不同年龄」，与「版本快照只读、历史可复现」冲突，且 AC-ADM-07-2 要的是「7 只命中 7 岁」的确定性；选项 3/4 正是 PRD 明确排除的区间合并口径（外部文库按单一周岁分册），会造成 7 岁与 8 岁混册。选 2 同时满足：后台 15 列年龄可复现、列表筛选精确、跨版本按各自生效日重算（过完生日换下一岁册）、`matchKey` 可回溯「外部按什么键匹配的」。

**后果**

- `age = calculateTalentAge(birthday, effectiveAt)`（复用 `server/utils/talent-matching.ts` 现成函数，只调用不修改；M3 同步也用同一函数）；0 岁合法；生日缺失/非法/未来 → 函数返回 `undefined`，该对象记 `failed(info_mismatch)`、不建建议行（无法形成有效匹配键；M3 基因报告侧 `?? 0` 的口径不改）。
- `age` 与 `matchKey`（`{name}｜{age} 岁`）冻结在建议行；发布/撤回不改；跨版本通过「接收新一版重建行」自然更新。
- 列表筛选 `age` 必须是整数（`"7"`），按冻结值**精确相等**；`"7-8"`、`"7 岁"` → 422；不提供年龄区间筛选。
- C 端展示 `ageLabel`（`N 岁`），不展示匹配键；M7 的「按建议选方向」等导航页不重算年龄。
- 单测覆盖：生日当天/前一天、2 月 29 日、未来生日、跨版本生日边界。

## D6 · 旧数据不迁移：旧培育内容口径不复用、不迁移、不双写；旧集合保留到 M6

**背景**

仓库现存旧天赋业务：`talent_cultivation_contents`（要素 × 分级 × 年龄/性别条件的内容库）、`talent_content_libraries`、`talent_elements`、`talent_cultivation_plans`、旧建议占位页 `app/pages/admin/talent/advice.vue`，以及旧 `/api/admin/talent/:resource` 动态路由。旧口径是「平台按规则匹配生成培育内容」，PRD 新口径是「外部按基因报告输出建议书」。两者字段、数据来源、更新节奏都不同。需要定死：旧数据怎么办、旧页怎么办、是否复用旧集合。

**选项**

1. 在旧 `talent_cultivation_contents` 上扩字段改造成建议域。
2. 新建 `talent_advice_versions` / `talent_advice_docs`，不迁移旧数据、不读不写旧集合；旧集合/旧页保留到 M6 统一删除。
3. 新建集合，同时把旧 `talent_cultivation_contents` 内容按规则回填成建议数据。
4. 新建集合，但建议弹层复用旧 `content` 作为「培育建议」段。

**结论**

选 2。理由：选项 1 会让一个集合同时承载「内容库规则匹配」与「外部整份建议书 + 版本」，语义不可调和，且旧集合已被旧页面/旧接口/旧 e2e 引用，改造必然破坏旧链路；选项 3 会把旧「按要素 × 分级」拼出的内容冒充外部建议原文，直接违反「正文只同步不改写」与客户验收口径，还制造不可追溯的版本；选项 4 同样把平台生成内容混进外部原文。选 2 让新域零历史包袱（PRD 原型本身是静态演示，没有真实历史建议数据需要保护），也符合 M3/ADR 0003-D6 的「旧数据过渡」处理方式。

**后果**

- 新建 2 个集合并只加不删；`scripts/setup.mjs` 建新库、`scripts/sync-talent.mjs` 存量库加集合/字段/索引/菜单权限；旧集合、旧页、旧 API、旧权限码全部保留到 M6。
- M5 新代码禁止读旧 `talent_cultivation_contents` / `talent_content_libraries` / `talent_elements`；实现审查用 `rg` 断言。
- 旧建议占位页 `app/pages/admin/talent/advice.vue` 由 M5 **原地改造**为正式列表页（不删除文件、不改菜单 path/component，避免路由与菜单漂移）；旧 `[resource].vue` 保留，M5 只新增静态 `advice/**` 路由并验证静态优先。
- 旧 `talent_elements` 的要素编码/名称**不进入**建议正文（BR-12 编码不对家长展示；建议正文为外部文案）。
- 不迁移、不回填、不建映射表；旧数据清理与旧权限码删除统一归 M6。

## 附：被否决的备选小结

| 决策 | 主要否决理由 |
| --- | --- |
| D1 单表 + 时间推断当前版 / 指针字段 / `isCurrent` 布尔 | 当前版不可靠或引入双真源；PB 层无唯一性约束；与硬约束「业务字段只落 `talent_*`」冲突（指针放 configs） |
| D1 允许手动归档/回切生效版 | PRD 只要求「回到当前生效版」的查看行为；回切会让 C 端内容与报告时间线错位，且需要重新处理撤回状态 |
| D2 一行一册 / 子表 sections / JSON 字符串 | 字段冗余 ×6、部分写入脏数据、放弃 PB JSON 查询与展示；「一册一份」是展示与编号派生，不是存储粒度 |
| D2 建议正文取 M1 要素/固定注解 | 正文来自外部文库，PRD 明确只同步不改写；M1 注解是报告要素解读用，混用会产生两套真源 |
| D3 同步后待发布 / 发布时重写正文 / 重复接收静默成功 | 违反「同步即默认已发布」「正文只同步不改写」；静默成功掩盖重复操作 |
| D4 报告撤回双写建议状态 / 页面层各自判断 / 落库 visible 字段 | 五条 M3 路径双写易漏、安全缺口；页面层不一致；定时任务有失效窗口，违反「立即失效」 |
| D5 查询时实时算年龄 / 区间匹配 | 历史不可复现、AC-07-2 不确定；区间匹配是 PRD 明确排除的旧口径 |
| D6 扩旧集合 / 回填旧内容 / 复用旧 content 作建议段 | 语义不可调和、破坏旧链路、冒充外部原文、违反「正文只改同步」 |
