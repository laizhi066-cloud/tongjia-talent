## 一、这个项目是干什么的

### 1.1 一句话定位

同佳天赋是一个**面向"天赋测评/成长画像"业务的 B/C 全栈平台**：第三方测评机构产出结果 → 平台转成结构化报告与要素解读 → 匹配培养方向与培养计划 → 由代理商/服务商机构在授权范围内服务会员 → 家长在微信小程序/H5 上读报告、选计划。

它不是通用后台脚手架。仓库说明（`AGENTS.md`）仍按 Foundation 基线描述"不含行业模块"，但本分支实际是在该基线上落地了完整的**天赋专项**领域模型、接口和页面。

### 1.2 三类使用角色

| 端 | 使用者 | 主要动作 |
| --- | --- | --- |
| 平台管理端（B 端，Nuxt 4 + Naive UI） | 平台运营/系统所有者 | 机构与账号授权、会员登记与导入、天赋规则（分类/要素/分级/内容库/匹配规则）、报告接收与整份发布/撤回、培养计划审核、同步配置与日志 |
| 机构端（B 端，同一工程 `/org/*`） | 代理商（引流方）、服务商（培养方，即培训机构） | 代理商：登记并查看自己引流的会员；服务商：维护培养计划、查看被授权推送的会员与报告。数据范围由服务端按机构归属强校验 |
| C 端（uni-app，H5 + 微信小程序） | 家长 / 本人 | 登录、本人/多子女视角切换、已发布报告阅读、要素解读（按分类/搜索）、阅读进度、培养计划推荐与单选提交、资料与协议 |

### 1.3 核心业务链路（已实现并实测）

```text
第三方测评 → 报告接收(webhook/定时拉取)
          → 按内部模板校验必需要素
          → 结果→分级→固定注解→年龄/性别→培育内容 匹配链
          → 固化条目快照（matchStatus/matchReason/matchConditions）
          → 平台整份发布（弹框选择开放分册）
          → C 端已发布报告 + 要素解读 + PDF（权限代理）
          → 按会员培养方向 × 已审核服务商计划 生成推荐（默认最多 3 条）
          → C 端单选计划（pending_review）→ 平台审核 → 建服务商授权 → pushed
```

关键业务规则（与代码一致）：

- 报告状态只有 `待发布 / 已发布 / 已撤回 / 异常`；C 端只读已发布报告与已开放分册。
- 报告 PDF 只存私有存储 key，B/C/机构访问一律走 Nitro 权限代理；撤回、授权取消、机构停用后代理即失效。
- 代理商与服务商由平台**直接配置** `institutionType`，不存在机构自助申请/资格材料/审核 SLA 流程。
- 培养计划直接绑定服务商（服务商即培训机构），系统中没有"培训机构/课程/课表/报名"实体。
- AI 只能生成计划草稿，必须人工确认并走平台审核，不参与分级与报告结论。

### 1.4 范围与商务口径

`docs/implementation/天赋功能验收映射.md` 记录本次专项报价口径：**平台管理端 72,000 + 机构业务端 41,000 + C 端 15,000 = 128,000 元**，共 826 条报价功能行。检测样本、实验室、送检、物流不在范围内，只接收第三方结果。

## 四、缺陷清单

### P0 — 阻断"从零交付"，必须处理

**P0-1 `talent:agent:member` 死权限码导致新库初始化必然失败（已修复）**

- 位置：`scripts/setup.mjs:133`（`FOUNDATION_RBAC_PERMISSION_CODES`）
- 现象：任何全新数据目录执行 `pnpm env:setup` 都会在最后的自检阶段抛 `基础版初始化未完成，缺少 RBAC 权限菜单：talent:agent:member`，数据库处于半初始化状态
- 根因：该权限码只存在于校验数组，`FOUNDATION_ACTION_MENU_DEFS` 未定义对应菜单，`server/` 与 `app/` 无任何引用，`role_menus` 也未分配
- 影响：**换机器、换库、CI 初始化全部失败**；本机之所以能跑，是因为沿用了历史库
- 处理：删除该行（1 行），初始化恢复；已实测 40 集合建成
- 建议：在 `test/foundation-schema.test.ts` 增加"每个权限码必须有对应菜单"的断言，避免再次漂移

**P0-2 `.env` 与 `.deploy.env` 已进入版本控制，含生产凭据**

- 位置：仓库根 `.env`、`.deploy.env`（`git ls-files` 确认为跟踪文件）
- 内容：阿里云 OSS AccessKeyId/Secret、PocketBase 超管口令、服务器 `root` SSH 口令、`ENCRYPTION_KEY`
- 影响：仓库一旦被共享/转让/泄露，生产存储与服务器直接失守；`.gitignore` 对已跟踪文件无效
- 建议：`git rm --cached .env .deploy.env` → 轮换全部密钥 → 统一用 `.env.example` + 部署期注入；仓库历史可用 `git filter-repo` 清理

### P1 — 影响验收与可重复交付

**P1-1 E2E 02 套件不可重复执行**

- 位置：`scripts/e2e/02-admin-actions.mjs:274`
- 现象：首轮 74/74 通过；复跑 72/74，失败项 `管理员新增机构可直接配置为服务商`（`Failed to create record.`）与级联的 `管理员直接切换机构类型为代理商`（404）
- 根因：用固定 `institutionNo: 'E2E-DIRECT-CONFIG'` 建机构且不清理，第二次触发唯一约束（服务端行为正确，是测试不幂等）
- 影响：同一环境无法连续验收两次；CI 二次运行必红
- 建议：用例内改用随机编号，或在 `finally` 中删除；全套件统一"自建自清"

**P1-2 客户管理员可见"系统管理"分组**

- 位置：`scripts/setup.mjs:1826`（`机构管理` 的 `parentId` 固定挂到 `系统管理`）
- 现象：`admin` 客户管理员登录后侧边栏出现"系统管理 > 机构管理"，而 `scripts/seed-accounts.mjs` 文件头明确写"系统不可见"，E2E 05 也断言不可见

- 建议：把"机构管理"移入"天赋规则"或独立的"机构与授权"分组；清理不可达分支；补一条"客户管理员菜单不含系统管理"的单测

## 五、总体结论

**1. 业务侧：主链路已闭环，可演示、可验收。**
"第三方结果 → 报告固化 → 平台发布 → C 端阅读/解读 → 计划推荐 → 单选提交 → 平台审核 → 服务商授权"这条链路，在数据、接口、权限、页面四层都有真实实现和实测证据；代理商/服务商数据隔离、C 端跨账号访问控制、PDF 权限代理均按设计生效。

**2. 工程侧：交付链尚未闭环。**
本分支"能跑"依赖一台已有历史数据库的机器：全新库初始化必然失败（P0-1，已修复为 1 行改动），E2E 不能连跑两遍（P1-1），生产密钥躺在仓库里（P0-2）。这三条决定了"把项目交给另一个人/另一台机器"这件事目前是不可靠的。

**3. 建议的收口顺序：**
① 确认 P0-1 修复入库并补测试 → ② 清理并轮换 `.env`/`.deploy.env` 凭据 → ③ 修 E2E 幂等与 Playwright 前置 → ④ 修"系统管理"菜单归属 → ⑤ 回扫 `AGENTS.md` / `docs/API.md` / `docs/ARCHITECTURE.md` → ⑥ 再做"删库重建 + 全量 E2E + 构建"的一键交付验收。
